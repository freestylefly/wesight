# 发布规范

本文档定义 WeSight 的最小发布流程。

## 发布门禁

发布稳定版前，必须运行并记录结果：

```bash
npm run build
npm run lint
npm test
```

任一门禁失败时，不得发布稳定版。若仍需要共享候选版本，必须把失败项写入已知问题或阻断项。

## Changelog

每个版本都必须在 `CHANGELOG.md` 中记录：

- 版本
- 日期
- 新增
- 变更
- 修复
- 已知问题

GitHub release note 应从 `CHANGELOG.md` 的对应版本条目生成。

## 发布审查

打 tag 前确认：

- 版本号与包元数据一致。
- 已知问题明确、可行动。
- 发布说明只描述对开发者或用户有意义的项目级变化。
- 涉及安全、签名、校验和平台差异时，已有对应检查记录。

## macOS 恢复构建

`macOS Release Recovery` 工作流可以对已有标签单独恢复一个 Mac 架构。传入 `release_tag` 和 `arch`，例如 `v1.0.12` 与 `x64`。

恢复工作流从指定标签检出应用源码，并从工作流提交中加载公证脚本。构建前会检查差异仅涉及公证脚本，构建后记录应用源码提交和公证脚本提交，并运行签名、公证、票据与安装包校验。

恢复产物可与同一标签下其他已通过校验的平台产物汇总，生成 SHA256 校验和后发布。失败任务保留应用签名归档和 DMG，公证请求 ID 记录在任务日志中。

应用已获 Apple 接受、票据下载却因网络失败时，可传入 `archive_run_id`、`archive_name` 与 `archive_request_id`，从保留的签名归档恢复。工作流核对 Apple 公证日志中的归档 SHA256 与版本，重新附加并校验票据，然后直接生成 DMG。此恢复步骤使用 Apple Silicon 构建机处理归档，两种应用架构均通过对应的安装包校验。
